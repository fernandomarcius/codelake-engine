# DataFusion 53 × 54 (front/df54 `cf34a2d`) × Trino 431 — SF10 — 2026-09-25

Re-measurement of front/df54 at its current HEAD `cf34a2dbafa7` (DataFusion 54.1 plus the follow-up: PostgreSQL wire operand checks, stable tests) against the committed DataFusion 53.1 baseline `3a54dcb0afbb` (integ/final), with the same harness and limits as `2026-09-25-df53-vs-df54-sf10.md` (which measured the earlier front/df54 commit `0b0b0ff`). All numbers are **measured** by `scripts/bench/run.sh`; nothing is estimated.

## Verdict

- **Correctness**: 33/33 cases match Trino 431 on `cf34a2d`, as on DF53; no case changed status. No engine container died (highest per-case peak 2533 MiB, container limit 8192 MiB).
- **Time**: geomean p50 of CodeLake −2.3% (DF54 vs DF53), p95 −9.7%, CPU −1.9%, memory −6.3%. Trino moved −1.8% (p50) between the DF53 run and this one.
- **bench-gate: BLOCK** on `meta_tables` (+46.9%), `meta_schemata` (+33.0%) and `meta_columns` (+28.2%); WARNING on `meta_column_types` (+17.0%); the other 29 cases PASS. The gate is reported as it came out and is not overridden here.
- **High-repetition re-run of the three BLOCK cases** (10 rounds × 200 repetitions, alternating DF53 and DF54, below): the slowdown is **not confirmed at the gate's scale**. Pooled medians DF54 vs DF53: `meta_schemata` +7.7% (95% CI [−5.1%, +23.3%]), `meta_tables` +8.6% ([−0.4%, +19.1%]), `meta_columns` +2.6% ([−6.8%, +14.1%]); per-round Mann-Whitney p = 0.24 / 0.076 / 0.27; DF54 slower in 6, 7 and 6 of 10 rounds. Every interval includes a slowdown under 10%, none excludes zero at the round level, and none reaches the 25% BLOCK threshold. A small shift of +0.07 to +0.19 ms per statement is plausible (the pooled repetitions lean to DF54 being slower, p ≤ 0.02, but repetitions inside one container are not independent).
- **Caveat**: both full DF54 runs (`0b0b0ff` in the earlier report, `cf34a2d` here) put the metadata cases 0.1–0.5 ms above the single DF53 full run, in the context the gate measures (after TPC-H, 10 repetitions): p50 `meta_tables` 0.96 ms on DF53, 1.42 and 1.41 ms on the two DF54 runs. The high-repetition protocol runs the metadata workload alone on a fresh engine, where the harness adds 1–2 ms per statement on both sides, and the DF53 full run was not repeated. Whether to accept the BLOCK as noise of sub-2 ms cases, re-run DF53 in full, or change how the harness measures sub-millisecond cases is a human decision (the gate, its thresholds and the baselines were not changed).

## How it was measured

- Temporary worktree (`git worktree add --detach`) of `cf34a2d` (front/df54 HEAD, DataFusion 54.1.0 in `Cargo.lock`) with the same bench harness overlay as `2026-09-25-df53-vs-df54-sf10.md`: `crates/codelake-bench`, `scripts/bench/run.sh` and `docs/benchmarks.md` from `3b8a3bf`, hence the `-dirty` commit in the baseline. No engine code was touched. A second temporary worktree of `3a54dcb` (DataFusion 53.1.0) with the same overlay served the DF53 arm of the high-repetition re-run.
- Release binaries built in the toolbelt image with the harness default `CARGO_PROFILE_RELEASE_DEBUG=0 CARGO_PROFILE_RELEASE_LTO=off`, one target volume per worktree.
- Same limits and workloads as the DF53 baseline run: `BENCH_SCALE=10 BENCH_CPUS=8 BENCH_MEMORY_MIB=8192`, warmup 1 + 5 measured repetitions (micro-batch 30, metadata 10, CTAS 3, incremental insert 10, as in the workload files), Docker volume `codelake-bs-sf10` (TPC-H SF10 written by Trino 431), each phase in a fresh container; TPC-H 22, pipeline/CTAS 4, micro-batch 3, metadata 4; memory ceiling = 8 GiB container, CodeLake pool 6 GiB.
- Only DF54 was run in full (05:02–05:26 GMT-3, under the global heavy lock, with its own Trino 431 phase). DF53 is the committed baseline `bench/baselines/3a54dcb0-df53-sf10.json` (run 01:53–02:17 the same night); its full run was not repeated. The two Trino columns (Trino next to DF53, Trino next to this run) show the drift of the machine between the two runs.
- Bench gate: `cargo xtask bench-gate --e2e bench/baselines/3a54dcb0-df53-sf10.json bench/baselines/cf34a2d0-df54-sf10.json` (the new baseline is versioned next to this report; the gate, its thresholds and the DF53 baseline are unchanged).

## BLOCK cases: high-repetition re-run (not a gate input)

Right after the gate, still under the heavy lock (05:26–05:34 GMT-3), only the three BLOCK cases were measured again: 10 rounds alternating DF53 (`3a54dcb`) and DF54 (`cf34a2d`), DF53 first in odd rounds and DF54 first in even rounds, a fresh engine container per arm per round, 20 warmup + 200 measured repetitions per case, same limits (`BENCH_WORKLOADS=metadata BENCH_CASE_REPS=meta_schemata=200/20,meta_tables=200/20,meta_columns=200/20,meta_column_types=1/0 BENCH_PHASES=codelake`). `meta_column_types` (WARNING) ran once, last, and is not analysed. Other projects' containers used 100–143% CPU of the 18-CPU VM before each phase. The metadata workload runs alone on a fresh engine here (in the full run it follows TPC-H), so absolute values are higher than in the gate.
