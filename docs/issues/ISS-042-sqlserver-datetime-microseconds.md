# ISS-042 — SQL Server `datetime` read as a microsecond timestamp; hive write refuses it

- Kind: defect · Recorded: 2026-09-26 · Status: open
- Context: SQL Server `datetime`, `datetime2` and `smalldatetime` all map to `Timestamp(Microsecond)` (`crates/codelake-connectors/src/sqlserver/types.rs`). The reference maps `datetime` to `timestamp(3)` (value rounded to the millisecond, as the JDBC driver reads it), `smalldatetime` to `timestamp(0)` and `datetime2(n)` to `timestamp(n)`. A `CREATE TABLE AS` into the hive catalog (millisecond precision) then fails with "Incorrect timestamp precision for timestamp(6); the configured precision is MILLISECONDS".
- Evidence: Cycle 1: 38 of the 50 failed models failed on this (every CDC pull with a `datetime` column, `lsn_time_mapping` included). Same value read differently: `2026-09-26 19:53:49.847` (reference) vs `19:53:49.846667` (candidate). Cycle 2 worked around it in the project copy with `CAST(... AS timestamp(3))` in `select_iceberg_safe`.
- Recommendation: Map each SQL Server temporal type to the precision it declares (`datetime` → millisecond, rounded as SQL Server converts to `datetime2(3)`; `smalldatetime` → second; `datetime2(n)` → n), with values tested against the reference on the three types. Keep the hive refusal of a wider precision: it protects data (no silent truncation).
- Revisit when: Done when the pulls run unmodified against CodeLake and the values match the reference.
