# ISS-018 — Case-preserving names, case-insensitive resolution

- Kind: removed limitation · Accepted by: Fernando Farias, 2026-09-25 · Status: awaiting-confirmation (implemented 2026-09-26; choices below applied by recommendation)
- Context: Hive names are folded to lower case because the reference engine does.
- Accepted: Preserve the case a name was written with, resolve names without regard to case, and refuse two names that differ only by case; no compatibility mode.
- Risk: Readers with case-insensitive collations (SQL Server OPENROWSET) would otherwise read the wrong column.
- Revisit when: Done when implemented with tests over hive and OPENROWSET readers. Implemented 2026-09-26 (ADR 0007): Parquet files carry each column as written; the metastore keeps folded names and records the written one as `codelake.name` (column property; table, view and schema parameter); every spelling resolves, on both client protocols and in expressions, `INSERT` column lists and `USING` lists (red-team 2026-09-26: the last two and the whole PostgreSQL wire failed; unquoted non-ASCII capitals were folded to ASCII lower case only); names that differ only by case are refused with an error naming both; old tables unchanged. Tested with Trino 431 (reads, and appends rows `CodeLake` reads) and SQL Server 2022 `OPENROWSET` (right columns under both spellings).
- Choices applied by recommendation (confirm or overturn):
  1. Metastore names stay folded, the written name goes to `codelake.name`: Trino 431 fails its `INSERT` into a table whose `dataColumns` hold a mixed-case name (checked: `NullPointerException: "type" is null`), which would break the reference engine writing shared tables (canary, rollback).
  2. Schema and table directories stay folded: Trino looks a table up only in its lower-case directory, and a case-sensitive file system would otherwise hold two directories for one name.
  3. The SQL surface (result headers, `information_schema`, `DESCRIBE`) shows folded names: showing the written case needs case-insensitive column resolution in the planner (DataFusion 54 matches names exactly); open as follow-up.
  4. View column names stay folded (a view writes no file).
- Views another engine stored (2026-10-01): Trino 431 stores a view's columns as its query spelled them (`analytics.obras_latest` stores `Descr_obr`; 40 of the 84 production views store a capital letter) and resolves any spelling of them, quoted or not; `analytics.vw_recebidas_comissoes_base1` reads `ob.descr_obr` and `CodeLake` refused it (`COLUMN_NOT_FOUND`), as it exposed the stored spelling. A view's columns are now exposed by their folded names, like a table's (`view_fields`): `descr_obr`, `Descr_obr`, `"Descr_obr"`, `"DESCR_OBR"` all resolve, through views over views, joins and aliases; `DESCRIBE` and `information_schema.columns` show `descr_obr`, as Trino 431 does (checked on `trinodb/trino:431`). Two stored names that differ only by case (Trino 431 creates such a view, then refuses every reference to its columns as ambiguous) refuse the view with an error naming both. Remaining divergence, the follow-up of choice 3: the header of `SELECT *` over such a view is the folded name (Trino 431 shows `Descr_obr`); rows and types are the same.
- References: ADR 0007.
