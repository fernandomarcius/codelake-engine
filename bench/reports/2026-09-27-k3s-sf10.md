# TPC-H SF10 on the k3s cluster — single node, distributed, Trino 431 — 2026-09-27

Branch `front/m4-distributed` (ADR 0011 spike and F14 implementation). Measured
on the project's k3s test cluster; every engine in its own pod with Guaranteed
QoS (CPU and memory requests equal to limits), results checked against Trino
431 with `codelake-bench compare` before any timing is read.

## Verdict

- **The large gain is the allocator, not distribution.** jemalloc was built to
  return every freed page at once (`dirty_decay_ms:0`): each free was an
  `madvise` and the next allocation page faults. With freed pages kept for up
  to a second while the pool is below an eighth of its limit (and returned at
  once above it, so the memory ceiling holds), TPC-H SF10 on 16 vCPU takes
  **2.6× less time and 65% less CPU**: sum of p50 51.6 s → 19.8 s, CPU 507 s →
  178 s. Against Trino 431 on the same pod size: 19.8 s against 24.4 s, 178 s
  of CPU against 243 s, 1.4 GiB mean peak memory against 23 GiB.
- **Distribution does not pay on this cluster.** Pod-to-pod bandwidth between
  the two nodes is 0.33 Gbit/s (iperf3, WireGuard overlay), against 43.6 Gbit/s
  within a node; ADR 0011 asks for 10 Gbit/s or more. Scan-heavy queries
  scale with a second worker (Q01 3.34 s → 1.48 s, Q06, Q12–Q15, Q19); every
  query that shuffles a join between the nodes gets several times slower (Q05,
  Q07–Q09, Q17, Q18, Q21). Four workers did not fit the cluster's free CPU.
- **Correctness:** 22/22 match Trino 431 on single node and distributed. The
  first distributed runs on two and four workers returned twice the rows on
  Q11, Q15 and Q22 (a nested loop join against one row, run once per task);
  fixed in `dd2248d` (the coordinator runs its wrapping rules after
  distribution) and re-measured.
- **The decimal work** (`avg` in 128 bits, kernel powers of ten per batch)
  accounts for ~7% of the gain (48.1 s against 51.6 s with the old allocator).

## How it was measured

- Cluster: 2 nodes, AMD EPYC 9J14 (KVM), 32 vCPU / 128 GiB each; k3s v1.36.
  The F8 shadow run shared the first node (about 20 vCPU reserved, busy one
  minute in five); single-node engines and one-worker runs used the second.
- Data: TPC-H SF10 written by Trino 431's `tpch` connector into a Hive
  warehouse (`codelake-bench generate`, 95 s), copied to the same path on both
  nodes (layout L1 of ADR 0011).
- Engines: Trino 431 with 64 GiB (query memory 75% of an 80% heap);
  CodeLake with `memory.limit` = 75% of the pod, `target_partitions` = vCPU;
  distributed: coordinator 4 vCPU / 16 GiB, workers 6 vCPU / 24 GiB.
- Client: `codelake-bench run` over the PostgreSQL wire (CodeLake) and the
  Trino HTTP protocol (Trino), 1 warmup + 3 repetitions, memory sampled from
  each pod's cgroup every 20 ms.
- Release binaries built on the cluster (`cargo build --release`, x86-64
  baseline; an `x86-64-v4` build was 6% faster and is not the default).
