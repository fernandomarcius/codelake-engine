# DataFusion 53 × 54 × Trino 431 — SF10 — 2026-09-25

Back-to-back measurement of the dependency train change (ROADMAP F11): `3a54dcb0afbb` (integ/final, DataFusion 53.1) against `0b0b0ffcaa14` (front/df54, DataFusion 54.1), both on TPC-H SF10 against Trino 431. All numbers are **measured** by `scripts/bench/run.sh`; nothing is estimated.

## Verdict

- **Correctness**: 33/33 cases match Trino 431 on DF53 and on DF54; no case changed status. No engine container died in either run (memory ceiling held: highest per-case peak 2524 MiB on DF53, 2314 MiB on DF54, container limit 8192 MiB).
- **Time**: geomean p50 of CodeLake −1.8% (DF54 vs DF53), p95 −11.0%, CPU −1.5%. Trino alone moved −10.6% between its two runs on the same machine, so differences under ~10% per case are not distinguishable from noise here.
- **Memory**: geomean per-case peak −7.4%, mostly TPC-H Q4 (1651 → 211 MiB).
- **Changes above 10%**: faster on DF54 — `mb_lineitem_window_rows` −42%, `tpch_q04` −27%, `ctas_revenue_mart` −17%. Slower on DF54 — the four `information_schema` cases, +22% to +48%, i.e. +0.1 to +0.5 ms on statements of 0.5 to 1.7 ms (CPU also +0.1 to +0.5 ms).
- **bench-gate: BLOCK** on `meta_tables` (+47.7%) and `meta_column_types` (+42.4%); WARNING on `meta_schemata` and `meta_columns`; every other case PASS. The gate is reported as it came out and is not overridden here. An alternated re-run of only those cases (below) does not reproduce the slowdown; whether to accept it as noise, re-measure the metadata cases with more repetitions, or investigate is a human decision.

## How it was measured

- Two temporary worktrees (`git worktree add --detach`): `3a54dcb` (DataFusion 53.1.0 in `Cargo.lock`) and `0b0b0ff` (DataFusion 54.1.0). Both got the same bench harness: `crates/codelake-bench`, `scripts/bench/run.sh` and `docs/benchmarks.md` from `3b8a3bf` (front/bench-scale, the harness of `2026-09-24-2b03934a039a-sf10.md`). Those paths are identical in both commits, so the overlay is the same three harness commits on each side; it is why the baselines carry a `-dirty` commit. No engine code was touched.
- Release binaries built in the toolbelt image with the harness default `CARGO_PROFILE_RELEASE_DEBUG=0 CARGO_PROFILE_RELEASE_LTO=off`, one target volume per worktree.
- `BENCH_SCALE=10 BENCH_CPUS=8 BENCH_MEMORY_MIB=8192`, warmup 1 + 5 measured repetitions (micro-batch 30, metadata 10, CTAS 3, incremental insert 10, as in the workload files), same data set (Docker volume `codelake-bs-sf10`, TPC-H SF10 written by Trino 431), each phase in a fresh container. Same workloads as the 2026-09-24 SF10 report: TPC-H 22, pipeline/CTAS 4, micro-batch 3, metadata 4; memory ceiling = 8 GiB container, CodeLake pool 6 GiB.
- Back to back under a single hold of the global heavy lock (`heavy.sh`), so no build or test of other checkouts ran in between: DF53 run 01:53–02:17, DF54 run 02:17–02:38 (GMT-3). Each run has its own Trino 431 phase. Containers of other projects (about 25 idle Postgres test containers and a few services) used 100–143% CPU of the 18-CPU VM before each phase; they are listed per phase under Environment.
- Bench gate: `cargo xtask bench-gate --e2e bench/baselines/3a54dcb0-df53-sf10.json bench/baselines/0b0b0ffc-df54-sf10.json` (baselines versioned next to this report).

## Metadata cases: diagnostic re-run (not a gate input)

To see whether the BLOCK reproduces, only the metadata workload was run again right after the gate, still under the same heavy lock: three rounds alternating DF54 → DF53, each round a fresh engine container, 5 warmup + 50 measured repetitions per case (`BENCH_WORKLOADS=metadata BENCH_CASE_REPS=meta_*=50/5 BENCH_PHASES=codelake`). The metadata cases run first on a cold engine here (in the full run they come after TPC-H), so absolute values are higher than in the table above. Pooled median over the 150 repetitions of each side, the three per-round p50s, and the median of the per-round CPU p50s (ms):

| meta_column_types | 2.64 | 2.92 | +10.3% | 2.78, 2.42, 2.27 | 2.59, 2.66, 2.94 | 2.08 | 2.31 |

The direction flips between cases and between rounds (−12% to +10%): at 1–3 ms per statement the run-to-run spread is larger than the difference the gate flagged. The full run's BLOCK is therefore not confirmed as a DF54 regression, but it is not disproved either: the full run also saw +0.1 to +0.5 ms of CPU per statement. If it is real, candidates are the per-statement checks added on front/df54 on top of DataFusion 54 (for example the operand-type check that now walks view bodies and the membership guard rule) — a hypothesis, not measured.
